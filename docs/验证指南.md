## 第 3 层 · 性能与「常量性」：核心卖点的量化证据

```powershell
python bench/bench_scale.py --modulus 1024 --l 32 --sizes 64,256,1024 --open-size 8 --reps 10
```

**期望**（关键三行）：

```
  承诺 C 的位长（各 n）    : [1021, 1022, 1024]   跨度 3 位
  证据 S_I 的位长（各 n）  : [1022, 1023, 1024]   跨度 2 位
  → 两者都约等于 |N|，与 n 无关（常量大小摘要 / 常量大小证据）

  n 增长 16 倍（|I| 固定为 8）：
    验证耗时 4.5 ms → 4.7 ms，比值 1.06x
    → 接近 1，说明验证时间与向量长度 n 无关（本方案的核心卖点）
```

**这一层证明了**论文 §5.2 的核心主张：**公开参数、证据大小、验证时间都不随向量长度增长**。

⚠️ **一个容易踩的坑**：`--open-size` **必须固定**。
如果你让它随 `n` 变（比如打开一半），量到的就是 `|I|` 的影响而不是 `n` 的影响 ——
`verify` 的代价是 `O(ell|I|)`，对 `|I|` 是线性的。
基准脚本的注释里专门写了这一点。

另外可以看分治的价值：

```powershell
# n = 1024 时分治比朴素快约 78 倍
python bench/bench_scale.py --modulus 1024 --l 32 --sizes 1024 --open-size 8 --reps 5
```

   > ⚠️ 「每块字节数」是在**建立会话**时定死的，所以改了它要重新点「① 建立会话」

1. **「▶ 一键跑完整流程」** → 日志里依次出现 ①②③④⑤⑥，右侧出现摘要面板、4 张服务器卡片、
   检索到的多份证据 → 聚合后的唯一证据 → **✓ 验证通过**
2. **「☠ 让服务器篡改内容」** → 该节点卡片变红、`本地视图不合法`；
   逐份验证显示 `失败(BAD_LAMBDA)`；**聚合被拒绝**
3. **「☠ 让服务器伪造证据」** → 逐份验证显示 `失败(BAD_S_I)`；**聚合同样被拒绝**

> 第 2、3 步里「聚合被拒绝」是**正确行为**，不是 bug：
> `VC.Agg` 合并前会做 `ShamirTrick` 同源自检，两份来自不同数据版本的证据根本不同源，
> 所以**连一个可验证的假证明都拼不出来**。

## 第 5 层 · 交叉验证：怎么确认这不是「自己跟自己自洽」

这是最有价值的一层。**「测试全过」本身不说明问题** ——
如果测试用的对照实现和被测实现犯了同一个错，测试会一起通过。
本项目用五种手段避免这件事：

### ① 每个数学函数都有**独立的暴力实现**做对照

`test_mathbase.py` 里不调用被测函数来验证它自己，而是另写一份最笨的实现：

```python
# 例：batch_root_factor 的对照
expected = [pow(G, X // x, N) for x in xs]     # 老老实实一个个算
assert batch_root_factor(G, xs, N) == expected
```

`shamir_trick`、`multiexp`、`weighted_root_product`、`product_tree` 全都是这么测的。

### ② 分治路径 vs 朴素路径必须**逐位相同**

代码里刻意保留了两条路径（清单 PS：「前期使用 13 进行 debug，这里的 8 算大量内容更快，但是出错不好修」）：

```powershell
python -m pytest tests/test_scheme.py -k "批处理与朴素" -v
```

### ③ **真聚合必须等于「对新集合从零算一遍」**

这是整份测试里最重要的一条断言：

```python
merged = agg(crs_n, A, v_A, pi_A, B, v_B, pi_B)     # 走聚合算法
direct = open_subvector(crs_n, A|B, v, v)           # 直算
assert merged.S_I == direct.S_I                     # 逐位比较
assert merged.Lambda_I == direct.Lambda_I
```

如果只断言「聚合后能通过验证」，一个把 `Λ` 算错但在别处凑巧抵消的实现也可能蒙混过关。

### ④ 更新操作由**独立的验证器**背书

`test_updates.py` 每个用例都同时检查三件事：

1. 所有节点的 `check_local_view()` 仍然是 `True`
2. 客户端能检索任意子集，`retrieve_and_verify` 通过
3. 内容确实按预期变了（该改的改了、该删的没了、该加的加上了）

三条同时成立，更新公式就**不可能错** —— 因为 `svc.verify` 是独立实现，
它不关心更新是怎么算出来的。

### ⑤ 不跑测试，自己动手验一条核心恒等式

这是最硬的证据。下面这段代码**不调用项目里的任何验证函数**，
只用最朴素的模幂检查方案的两个基本恒等式：

```powershell
python -c "
from svc import *
r = DeterministicRNG(b'hand-check')
crs = setup(16, 16, 16, rng=r, modulus_bits=256)
sn  = specialize(crs, 16)
v   = [r.randbelow(1 << 16) for _ in range(16)]
pg, N = crs.primegen, crs.N

# 手算 S_I（不用项目函数）：S_I = g^(e_[n] / e_I)
e_all = 1
for i in range(16): e_all *= pg.get(i)
I = [2, 5, 9]
e_I = 1
for i in I: e_I *= pg.get(i)
S_I = pow(crs.g, e_all // e_I, N)

# 恒等式一：S_I^{e_I} = U_n
print('恒等式一  S_I^e_I == U_n :', pow(S_I, e_I, N) == sn.U_n)

# 恒等式二：用一个『没在 I 里』的下标算 1/e_I 次方（指数必须是整数）
j = 3
assert e_all % (pg.get(j) * e_I) == 0, '指数必须是整数，否则求不出根'
print('恒等式二  指数整除检查   :', True)
"
```

**期望**：两行都是 `True`。

这两条恒等式就是整个方案能成立的根基：

- **恒等式一**让验证方用**一次模幂**把 `S_I` 锁死；
- **恒等式二**说明「`1/e_I` 次方能公开算」的前提是 `j ∉ I` ——
  此时 `e_j·e_I|e_([n])`，**指数是整数，不需要求根**。

## 常见问题

**Q：要跑多久？**
A：测试 5 秒，演示约 6 秒（其中 3.5 秒是生成 2048 位 RSA 模数），性能基准约 10 秒。
演示想更快就把模数位长调小。

**Q：模数设成 512 位安全吗？**
A：**不安全**。512 位只够跑通代数关系，没有任何安全强度。
真实部署需要 2048 位以上。演示时设小只是为了快两个数量级。

**Q：为什么 `verify` 有时候几十毫秒、有时候上百毫秒？**
A：因为它是 `O(ell|I|)` —— 线性于**本次打开了多少块**，与文件总长度无关。
打开 5 块约 37 ms、打开 16 块约 115 ms，折算下来都是 ~7 ms/块。

**Q：`create_from()` 报 `NotImplementedError` 是 bug 吗？**
A：不是 —— 它**本来就是本方案不支持的能力**。`CreateFrom` / `GetCreate`
需要一个子向量知识论证，而那东西建立在「承诺是一对累加器」的代数结构上；
本方案（§5.2）把承诺压成了单个群元素，正是它参数更省的原因，
代价就是拿不到这个能力。两个占位方法（`StorageNode.create_from` /
`ClientNode.get_create`）会抛出带说明的 `NotImplementedError`。

**Q：那我的文件想派生一个小文件怎么办？**
A：当前版本没有这个能力。可行的替代做法是**对新子集重新承诺一遍**（`commit` 一次），
代价是客户端要重新拿一个摘要，而且无法向它证明「新文件确实取自原文件」。

**Q：上传文件和文本框内容有什么区别？**
A：页面第 1 节可以上传任意文件。文件走的是**原始字节**（前端转十六进制、
后端 `bytes.fromhex` 还原），所以图片/压缩包这类二进制内容不会被损坏；
不选文件时才用文本框的 UTF-8 编码内容。两者都只是「字节流」，
切块与承诺完全一致。

**Q：`agg` 报「ShamirTrick 失败」怎么办？**
A：绝大多数情况是**两份证据来自不同数据版本** —— 也就是有人改过数据。
这是设计中的自净能力，不是故障。另一种可能是素数映射发生了碰撞
（只有用哈希版 `PrimeGenHash` 且位数太小时才会出现）。
