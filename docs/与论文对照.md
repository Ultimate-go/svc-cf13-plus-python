## 一、SVC 部分（论文 §5.2）

论文 §5.2 的算法原文：

```
VC.Setup(1^λ, ℓ, n) → crs
    生成隐藏阶群 G ← Ggen(1^λ)，采样生成元 g，确定确定性抗碰撞函数 PrimeGen
    返回 crs = (G, g, PrimeGen)

VC.Specialize(crs, n) → crs_n
    计算 n 个 (ℓ+1) 比特素数 e_i ← PrimeGen(i)，Un = g^{e_[n]}
    返回 crs_n ← (crs, Un)

VC.Com(crs, v⃗) → (C, aux)
    对每个 i ∈ [n] 计算 S_i ← g^{e_[n]\{i}}
    然后 C ← S_1^{v_1} ··· S_n^{v_n}，aux ← (v_1, ..., v_n)

VC.Open(crs, I, y⃗, aux) → π_I
    对每个 j ∈ [n] \ I 计算 S_j^{1/e_I} ← g^{e_[n]\(I∪{j})}
    以及 S_I ← g^{e_[n]\I}
    然后 Λ_I ← ∏_{j∉I} (S_j^{1/e_I})^{y_j}
    返回 π_I := (S_I, Λ_I)

VC.Ver(crs, C, I, y⃗, π_I) → b
    解析 π_I := (S_I, Λ_I)，对每个 i ∈ I 计算 S_i = S_I^{e_{I\{i}}} = Un^{1/e_i}
    接受 ⟺ S_I^{e_I} = Un  ∧  C = Λ_I^{e_I} · ∏_{i∈I} S_i^{y_i}

VC.Disagg(crs, I, v⃗_I, π_I, K) → π_K
    S_K ← S_I^{e_{I\K}}
    对每个 j ∈ I \ K：χ_j = S_K^{1/e_j} ← S_I^{e_{I\(K∪{j})}}
    返回 π_K := (S_K, Λ_K)，其中 Λ_K ← Λ_I^{e_{I\K}} · ∏_{j∈I\K} χ_j^{v_j}

VC.Agg(crs, (I,v⃗_I,π_I), (J,v⃗_J,π_J)) → π_K      （K = I ∪ J，I ∩ J = ∅）
    S_K ← ShamirTrick(S_I, S_J, e_I, e_J)
    φ_j ← S_K^{e_{J\{j}}} (j ∈ J)，ψ_i ← S_K^{e_{I\{i}}} (i ∈ I)
    ρ_I ← Λ_I / ∏_{j∈J} φ_j^{v_j}，  σ_J ← Λ_J / ∏_{i∈I} ψ_i^{v_i}
    Λ_K ← ShamirTrick(ρ_I, σ_J, e_I, e_J)
```

### 统一视角：证明就是摘要

除了论文 §5.2 的叙述，Catalano-Fiore 方案还有一种更本质的看法
（参考 `2020-11-24-Catalano-Fiore-Vector-Commitments`）：

> **子向量打开证明 :math:`\pi_I` 就是「去掉 I 之后那个向量的摘要」。**

即 :math:`\pi_I = d(\\mathbf{v} \\setminus I)`，其中

.. math::
    d(\\mathbf{v}) = (S, \\Lambda), \\quad
    S = g^{e_{[n]}}, \\quad
    \\Lambda = \\prod_{i \\in [n]}\\left(S^{1/e_i}\\right)^{v_i}

对照到论文 §5.2 的记号：:math:`S = U_n`、:math:`\\Lambda = C`
（两者都是两个群元素，正是 VDS 摘要 :math:`\\delta = ((U, C), n)` 的那两个）。

这一条在实现上是**真的合并了代码路径**，不是只换了个说法：

| 操作 | 统一视角 | 实现位置 |
|---|---|---|
| 承诺 | :math:`d(\\mathbf{v}\\setminus\\varnothing) = (U_n, C)` | `digest_of(crs_n, vals)` |
| 打开 | :math:`d(\\mathbf{v}\\setminus I) = (S_I, \\Lambda_I)` | `digest_of(crs_n, vals, I)` |
| 拆分 | 把 :math:`I\\setminus K` 逐个「加回去」 | `disagg` → `add_back` 循环 |
| 验证 | 把 :math:`I` 全加回去，看是否变回 :math:`d(\\mathbf{v})` | `verify` → `add_back` 循环 |
| 追加新位置 | 对 :math:`d(\\mathbf{v})` 加回一个位置 | `add_back` |

「加回」这一步只有一个公式：

.. math::
    (S, \\Lambda) \\leftarrow \\bigl(S^{e_i},\\; \\Lambda^{e_i}\\cdot S^{v_i}\\bigr)

（:math:`S^{v_i}` 用**更新前**的 ``S``）。它与论文 §5.2 的公式**代数上等价**，
但代价从 :math:`O(\\ell|I|^2)`/::math:`O(\\ell|I|\\log|I|)`
降到 :math:`O(\\ell|I|)`。

#### 为什么等价

论文的 ``VC.Disagg`` 写的是:

.. math::
    \\Lambda_K = \\Lambda_I^{e_{I\\setminus K}} \\cdot
    \\prod_{j \\in I\\setminus K} \\chi_j^{v_j},\\qquad
    \\chi_j = S_I^{\\,e_{I\\setminus K}/e_j}

令 :math:`E = I \\setminus K`。逐个加回时，第一个位置 :math:`i_1` 给出
:math:`\\Lambda^{e_{i_1}}\\!\\cdot\\! S^{v_{i_1}}`；第二个位置 :math:`i_2` 再乘上
:math:`e_{i_2}`、并补一项 :math:`(S^{e_{i_1}})^{v_{i_2}}`……
展开后就是 :math:`\\Lambda^{e_E} \\cdot \\prod_{j\\in E} S^{\\,e_E/e_j \\cdot v_j}`，
而 :math:`S^{e_E/e_j}` 正是 :math:`\\chi_j`。逐项对应。

#### 顺带得到的几个好处

1. **验证从平方降成线性**。旧写法里 ``reconstruct_s_i`` 每次的指数有
   :math:`(|I|-1)(\\ell+1)` 位，:math:`|I|` 次就是 :math:`O(\\ell|I|^2)`；
   新写法每步指数只有 :math:`\\ell+1` 位。实测 :math:`|I|=512` 时
   **152.9 倍**加速（47.5 s → 0.31 s）。
2. **拆分不再需要一次 `root_factor`**，:math:`O(\\ell|I\\setminus K|)`。
3. **批量拆分改成递归二分**。Campanelli 等人描述的做法是
   「先取根（整向量证明 :math:`d(\\mathbf{v}\\setminus[n]) = (g, 1)`），
   再递归拆成两半」；他们在论文里报 :math:`O(\\ell n\\log^2 n)`，
   但用上面这个更快的拆分法实际是 :math:`O(\\ell n\\log n)`。
4. **向量扩展的公式现成可得**（见下）。

### 关于 PrimeGen 的一个取舍

论文原文：

> One can choose a different mapping to primes for PrimeGen and even just a
> bijective mapping (which is inherently collision resistant) would be enough:
> this is actually the instantiation we consider in our efficiency analysis.

所以默认用**双射**（`PrimeGen`）：从 `2^(bits-1)` 起向上扫描素数。
哈希版（`PrimeGenHash`）作为对照保留在代码里，并强制开启碰撞检测。

> **清单与位长的冲突（已按论文裁定）**
> 清单 #10 原文写「从 2 的 bits 次方开始向上扫描」，但同一份清单的记号表
> 要求「`e_i` 是第 `i` 个 `(l+1)` 比特的素数」，且「bits 取 `l+1`」。
> 若真从 `2^bits` 起步，扫出来的全是 `bits+1` 位素数，与位长要求矛盾。
> 论文写的是 `n (ℓ+1)-bit primes`，故**以论文为准**：
> 起点取 `2^(bits-1)`，`bits` 参数就是输出素数位长。

### 顺带验证到的一个性质

论文 §7 的正确性证明里有这么一句：

> a local view of a storage node (pp, δ, n, st, I, FI) is valid if

## 三、实现范围对照

### 1. §4.2 预处理提交与快速打开（`PPCom` / `FastOpen`）—— ✅ 已实现

论文 Fig. 2 的两个算法在 `svc/fastopen.py`：

```
VC.PPCom(crs, B, v):
    (C, aux) ← VC.Com(crs, v)                        → commit
    π*       ← VC.Open(crs, [n], v, aux)             → open_subvector（恒为 (g, 1)）
    π⃗        ← VC.DisaggOneToMany(crs, B, [n], v, π*) → disagg_one_to_many
    aux*     := (π_1, …, π_n', v);  return C, aux*

VC.FastOpen(crs, B, aux*, I):
    S ← 覆盖 I 的最小块下标集
    逐块 π'_j ← VC.Disagg(crs, P_j, v_{P_j}, π_j, I ∩ P_j)
    return VC.AggManyToOne(crs, ((I_j, v_{I_j}, π'_j))_{j∈S})
```

四点说明：

- 第 2 步的 `π* = VC.Open(crs, [n], v)` 在本方案里**恒为 `(g, 1)`**：
  `S_[n] = g^{e_[n]/e_[n]} = g`、`Λ_[n] = 1`（空集上没有值可累）。
  它只是形式上的中间量，真正的工作量全在第 3 步。
- `|S| ≤ min(|I|, ⌈n/B⌉)`；`B = 1` 时每个 `P_j` 是单点，
  `I_j = P_j`，那一步 `Disagg` 可以跳过（论文脚注 16 说的正是这件事）。
- 建议存储 `⌈n/B⌉·2|G|` 位，即论文的 `(n/B)·p(λ)`。
- **实测**（`n=512`、`|N|=512`、`l=32`、`|I|=8`）：`FastOpen` 36.1 ms，
  直接 `Open` 375.8 ms，**快 10.4 倍**；预处理 953.7 ms、32 块建议。

### 2. §8.2 的三处文件更新 —— ✅ 已实现（**两段式**）

论文把更新拆成 `PushUpdate`（产出 `Υ∆`）与 `ApplyUpdate`（校验 `Υ∆` 再应用）。
本实现在 `vds/updates.py` 里按这个结构落地：

| 论文算法 | 本实现 | 说明 |
|---|---|---|
| `StrgNode.PushUpdate` | `push_update()` | 持有改动内容的一方产出新摘要 + 新状态 + `Υ∆` |
| `StrgNode.ApplyUpdate` | `apply_update()` | **不读改动后的内容**，先校验 `Υ∆` 再算 |

论文 §8.2 的更新算法正文里用的是 **§5.1 的原语**（`Γ/∆`、`PartndPrimeProd`），
而 §8.2 的摘要却是 §5.2 的形式（`δ = ((U, C), n)`）——
那一段是从 §8.1 抄过来的、没真正改成 §5.2 的记号，**逐字转写做不到**。

本实现因此**从摘要代数独立推导**三个公式，并用独立的 `svc.verify` 逐步验证：

| `op` | 摘要 | 节点状态 | `Υ∆` |
|---|---|---|---|
| `mod` | `C' = C · ∏_{i∈K} S_i^{Δ_i}`，`U' = U` | 只对 `i ∈ K \ I` 修正 `Λ_I`；修正因子 `S_I^{1/e_i} = ShamirTrick(S_I, S_i, e_I, e_i)` | `(F_K 旧值, S_K)` |
| `add` | `(U', C')` = 对 `(U, C)` 顺序 `add_back` | `S'_I = S_I^{e_K}`，`Λ'_I = Λ_I^{e_K} · ∏_{j∈K} (·)^{v_j}` | `S_K = U`（旧累加器） |
| `del` | `δ' = π_K = d(v \ K)` | `K ⊆ I` 时 `(S_I, Λ_I)` **一个字都不用改**；`I ∩ K = ∅` 时做一次 `agg` | `(F_K, S_K)`，`S_K = δ'.U` |

**两处论文笔误**，代码里就地标注了：

1. `Υ∆` 的校验端。论文三种 `op` 都写 `b ← (S_K^{∏ e_j} = U)`，
   但 `add` 的 `S_K` 是**旧**累加器、论文自己又定义 `U' ← U^{∏ e_i}`，
   所以自洽的形式是 `S_K^{e_K} = U'`。`mod`/`del` 的 `= U` 没问题。
2. `add` 的 `C'`。论文写 `C' ← C · ∏ S_j^{F_j}`，
   但正确结果是 `C' = C^{e_K} · ∏(中间 S)^{v_j}`（就是要顺序 `add_back`）。

**一项比论文更强的检查**：`apply_update` 除了校验 `Υ∆`，
还要求**更新后的本地视图合法**。这不是多余 ——
`mod` 不改变 `U`，所以一份旧版本的 `Υ∆` 仍能满足 `S_K^{e_K} = U`，
单看那一条**重放攻击是过得去的**；但重放会把 `Δ` 按旧值重算一遍，
得到的 `C'` 与节点实际存着的数据对不上，本地视图检查立刻能看出来。

三个值得一提的推导结果：

- **`add` 之后新位置的证明就是旧摘要本身**：`π_K^new = d_new(v' \ K) = (U, C)`
  —— 因为「除 `K` 之外的其余部分」正是旧文件，所以不用算任何东西。
- **`del` 的新摘要直接就是拆出来的 `π_K`**，与论文 `δ' ← ((Γ_K, ∆_K), n')` 一致。
- **`del` 里只持有被删区间的节点，状态完全不变**：
  `S'_J = g^{e_[n']/e_J} = g^{e_[n]/(e_K · e_I/e_K)} = S_I`。

正确性由 `tests/test_updates.py`（21 个，系统级）与
`tests/test_update_protocol.py`（29 个，协议级）共同背书。

### 3. 附录 D.1 存储证明（PoR / PDP）—— ✅ 已实现

论文 D.1 的结论是这条构造对**任意** VDS 成立（"any VDS scheme admits a PoR
mechanism"），所以它直接架在 §8.2 之上。四个算法在 `vds/pos.py`：

| 论文 | 本实现 |
|---|---|
| `ClntNode.PoS-Challenge(n) → r` | `pos_challenge()` / `ClientNode.pos_challenge()` |
| `StrgNode.PoS-Prove(δ,n,st,I,F_I,r) → π_r` | `pos_prove()` / `StorageNode.pos_prove()` |
| `StrgNode.PoS-Aggregate(δ,r,π_{r,1},π_{r,2}) → (b,π_r)` | `pos_aggregate()` / `pos_aggregate_all()` |
| `ClntNode.PoS-Ver(δ,r,π_r) → b` | `pos_ver()` / `ClientNode.pos_ver()` |

外加论文 "Parallel Proof of Storage" 一节描述的并行版
（`parallel_pos_challenge()` / `parallel_pos_verify()`）：**一份挑战同时验 k 个等长文件**。

与论文的两点差异，都如实记在模块 docstring 里：

- **抽样不放回**。论文写 `r_1,…,r_λpos ←$ [n]`（可重复），
  本实现不放回，这样 `|r|` 恒等于 `λ_pos`，覆盖度更可预测。
- **并行版的收益不同**。论文说并行可摊薄 `U_r = g^{u_r}`（`u_r = ∏_{i∈r} e_i`）的计算，
  但那是 **§5.1** 的性质 —— 它的验证式里出现 `U_r`。
  §5.2 的验证走 `svc.verify` 的 `add_back` 迭代、`U` 直接取自摘要，
  **不需要**算 `e_r`。所以这里摊薄的是协议轮次而非群元素运算。

**攻击面**：少给（`Q ≠ r`，报「挑战未收齐」）、改内容、伪造证据 ——
后两者在**聚合阶段**就被 `ShamirTrick` 的同源自检拦住，连一份可验证的假证明都拼不出来
（`strict=True` 抛错；`strict=False` 跳过并最终报未收齐）。见 `tests/test_pos.py`（23 个）。

#### 4.1 为什么这两节一开始是空的

论文原文：

> Finally, for Υ_J it computes an argument of knowledge of subvector
> (see section 6), π_PoKSubV′ ← PoKSubV′.P(pp, (δ, δ′, J), (v⃗_J, π_I))
> and sets Υ_J ← (δ′, π_PoKSubV′).

> ClntNode.GetCreate(δ, J, Υ_J) → (b, δ′)
>   Parse Υ_J := (δ′, π_PoKSubV′), set n′ = |J|
>   Output b ← PoKSubV′.V(pp, (δ, δ′, J), π_J) ∧ J = {1, ..., |J|} ∧ δ′

`PoKSubV` 是论文 **§6** 的 Σ 协议，用来证明「我这个新摘要确实是从原文件的某个子向量
切出来的，没有夹带私货」。它并不独立于 §5.2 —— **它建立在 §5.1 阴阳方案之上**：

| PoKSubV 依赖的东西 | 来自 | §5.2 有吗 |
|---|---|---|
| CRS `(G, g, g₀, g₁, PrimeGen, Uₙ)` | §5.1 | ✗ 只有一个 `g` |
| 承诺 `C := ({A,B}, π_prod)` | §5.1 | ✗ `C` 是单个群元素 |
| `PartndPrimeProd(I, v⃗_I) → (a_I, b_I)` | §5.1 | ✗ 没有二元划分 |
| 打开证明 `(Γ_I, ∆_I)` | §5.1 | ✗ 是 `(S_I, Λ_I)` |

整套机制建立在「承诺是**一对**累加器 `A, B`」之上 —— 有了这一对，
才能把 `(a_I, b_I)` 分别塞进两条等式里做 AND 复合：

```
Γ_I^{a_I} = A  ∧  ∆_I^{b_I} = B            ← PoKOpen：v_I 打开了 C
        ∧
g₀^{a_I} = A' ∧ g₁^{b_I} = B' ∧ U_{n'} = g^{a_I·b_I}   ← PoProd：C' 用的是同一组 (a_I, b_I)
```

§5.2 把承诺压成单个群元素（这正是它参数更省的原因），
代价就是**失去了 PoKSubV 赖以存在的代数结构**。
所以要做它，必须先把整个 §5.1 实现出来（双生成元群、二元划分，
以及 `PoE` / `PoKE2` / `PoProd2` 三个子协议）。

当时的选择是直接抛 `NotImplementedError`：把 PoK 部分省掉后 `δ'` 与 `st'`
仍然算得出来，但客户端**无从核实**，这个算法就失去了全部意义。
主流程（commit → 分发 → 检索 → 聚合 → 验证）不依赖它，这样收尾是安全的。

**现在这三节都补齐了**（见 4.2 ~ 4.4）。实现的是 §8.1 的 `VDS1`，
它与 `vds/` 目录下的 `VDS2` **并列**，不是替换关系：

|  | `VDS2`（§8.2） | `VDS1`（§8.1） |
|---|---|---|
| 摘要 | `((U, C), n)` | `((A, B), n)` |
| 本地状态 | `(S_I, Λ_I)` | `(Γ_I, Δ_I)` |
| 承诺大小 | **1** 个群元素 | 2 个群元素 |
| 打开证明 | **2** 个群元素 | 2 个群元素 |
| 需要 `VC.Specialize` | 是（`U_n` 进摘要） | 否 |
| 派生新文件 | ✗ 没有这个算法 | ✅ `CreateFrom` / `GetCreate` |

#### 4.2 §5.1 阴阳方案

核心是把「承诺一个比特向量」拆成「为两个划分各建一个 RSA 累加器」：

```
S₌₀ = { i ∈ [n] : v_i = 0 }        S₌₁ = { i ∈ [n] : v_i = 1 }
A = g₀^a   (a = ∏_{i ∈ S₌₀} p_i)   B = g₁^b   (b = ∏_{i ∈ S₌₁} p_i)
```

关键不变量是 `a · b = u_[n]`（两个划分的素数乘积相乘恰好是全体），
所以光有 `(A, B)` 还不够 —— 敌手可以把同一个 `i` 同时塞进两个累加器。
承诺里必须再带一个 `PoProd2` 证明「这两个集合构成 [n] 的划分」。

| 论文算法 | 实现 |
|---|---|
| `VC.Setup(1^λ, {0,1}^k)` | `setup1()` —— 三个生成元 `g, g₀, g₁` |
| `VC.Specialize(crs, n)` | `specialize1()` —— `U_n = g^{u_n}` |
| `PartndPrimeProd(I, v)` | `partnd_prime_prod()`，每个比特位一组 `(a_j, b_j)` |
| `PrimeProd(I)` | `prime_prod()` |
| `VC.Com` / `Open` / `Ver` | `commit1()` / `open1()` / `ver1()` |
| `VC.Disagg` / `VC.Agg` | `disagg1()` / `agg1()` / `agg_many_to_one1()` |

打开证明满足 `Γ_I^{a_I} = A ∧ Δ_I^{b_I} = B` —— 这两条等式就是后面
`PoKSubV` 能做 AND 复合的全部依据。

块宽 `k` 也支持：每个块 `v_i ∈ {0,1}^k` 按**比特位**切成 `k` 组划分，
共 `2k` 个累加器，每位上 `a_j · b_j = u_[n]` 恒成立。

#### 4.3 §6 的五个知识论证

论文是三步 **Σ 协议**，这里统一用 **Fiat–Shamir** 转非交互式：
挑战 ℓ 用哈希到素数、随机底数 `h` 取 `g^t`（隐藏阶群里没有直接哈希到群元的办法）、
`α ← [0, 2^λ)` 用哈希取整数，全部吸附进一个 `Transcript`。

按论文脚注 17 的提醒，非交互版本的挑战素数取 **`2λ` 位**
（`λ` 位素数存在显式的平方根攻击）。

| 协议 | 证明的语句 | 实现 |
|---|---|---|
| `PoProd2`（Fig. 3） | `Y = g₁^a g₂^b ∧ C = g₃^{ab}` | `poprod2_prove` / `poprod2_verify` |
| `PoProd*`（Fig. 5 内联） | `A = Γ^a ∧ B = Δ^b ∧ C = g^{ab}`，底数由证明方给定 | `poprodstar_prove` / `poprodstar_verify` |
| `PoKOpen`（Fig. 5） | 我知道 `(v_I, π_I)` 且它打开了 `C` | `pokopen_prove` / `pokopen_verify` |
| `PoKSubV`（Fig. 6） | `C'` 承诺的正是 `C` 在 `I` 上的子向量 | `poksubv_prove` / `poksubv_verify` |
| `PoKComSub`（§6.3） | 两个承诺在 `I` 上共享同一段子向量 | `pokcomsub_prove` / `pokcomsub_verify` |

`PoKSubV` 验证式的最后一条值得单独说：

```
Q_C^ℓ · g^{r_c} = U_{n'}
```

其中 `a_I · b_I = u_I`。要让它等于 `u_{n'}`（新方案 `crsn'` 的定点累加器），
必须 `u_I = u_{n'}`，也就是 **`I` 恰好是前 `|J|` 个下标**。
这把「子向量必须是一个正常向量、而不是一般子向量」这条要求
直接编进了代数里 —— 也正是 `GetCreate` 要额外查 `J = {1, ..., |J|}` 的原因。

`PoKComSub` 论文说「把两次 `PoKOpen` AND 复合即可」，
但真要省下来，两次必须**共用同一组挑战** `h, ℓ, α`，
否则就退化成两个独立证明。所以本实现不是简单地调两次 `PoKOpen`，
而是把四条底数等式塞进同一个 `PoProd*`。

#### 4.4 §8.1 的 `VDS1`

摘要带的是**一对**累加器：

```
δ  := ((A, B), n)          ← 客户端只保存它
st := π_I := (Γ_I, Δ_I)    ← 存储节点的本地状态
```

| 论文算法 | 实现 |
|---|---|
| `Bootstrap(1^λ)` | `VDS1Session.bootstrap` —— `δ₀ = ((g₀,g₁), 0)`、`st₀ = (g₀,g₁)` |
| `VC.Com'` / `VC.Ver'` | `com_prime()` / `ver_prime()` —— **不带 PoProd2** |
| `VC.Disagg'` / `VC.Agg'` | `disagg_prime()` / `agg_prime()` |
| `StrgNode.AddStorage` / `RmvStorage` / `Retrieve` | `StorageNode1.add_storage` / `rmv_storage` / `retrieve` |
| `StrgNode.CreateFrom` | `StorageNode1.create_from` |
| `ClntNode.GetCreate` | `ClientNode1.get_create` |
| `StrgNode.PushUpdate` / `ApplyUpdate` | `StorageNode1.push_update` / `apply_update` |
| `ClntNode.ApplyUpdate` / `VerRetrieve` | `ClientNode1.apply_update` / `ver_retrieve` |
| `AggregateCertificates` | `ClientNode1.aggregate_certificates` / `aggregate_two` |

`CreateFrom` 为什么重要：一个只存了文件一部分的节点，
可以从中派生出一个**新文件** `F_J`，并且只用一个**常数大小**的
`PoKSubV'` 证明就让客户端相信「新摘要 `δ'` 承诺的确实是原文件在 `J` 上的那一段」。
内容根本不用传。

`mod` / `del` 的本地状态更新要按 `I ∩ K` 分三种情形（论文原文）：

* `I ∩ K = ∅`：两份状态做一次 `ShamirTrick`，`mod` 再把结果抬到 `a'_K`；
* `I ∩ K = K`：状态**一个字都不用改** —— 因为 `K ⊆ I` 时
  新值带来的指数因子在 `Γ_I = g₀^{a/a_I}` 里正好约掉；
* `I ∩ K = L ∉ {K, ∅}`：把 `K` 拆成 `L ⊔ L̄`，`L` 那半边不改变状态，
  只需对 `L̄` 做一次 `ShamirTrick`，`mod` 抬的指数是 **`a'_{L̄}`** 而不是整个 `a'_K`。

#### 4.5 三处与论文不一致的地方（已按代数自洽修正）

1. **`CreateFrom` 返回的 `st'`**

   论文正文写 `st' ← VC.Disagg(pp, I, F_I, π_I, J)`。
   算出来的是「`J` 在**旧**摘要 `δ` 下的打开」`g₀^{a_L}`，
   它满足 `Ver'(δ, J, F_J, ·)` 但**不**满足 `Ver'(δ', J, F_J, ·)` ——
   那要 `a_L = 1` 才碰巧成立。

   论文自己的正确性证明要求 `(pp, δ', n', st', J, F_J)` 是**合法本地视图**
   （“validity ... comes from correctness of VC.Com′”），
   所以本实现取**新摘要下的打开**。因为 `J` 被要求是前缀（新文件的全部下标），
   那份打开就是根打开 `(g₀, g₁)`，与 `st₀` 同形。

2. **`op = add` 时发布者的 `st'`**

   论文写 `st' ← st`，理由是 `π_I = π'_J`。这个理由本身不成立（只在
   `a'_K = 1` 时对），但**结论是对的**：`J = I ∪ K` 时
   `Γ_J = g₀^{a·a'_K/(a_I·a'_K)} = Γ_I`，新增位置带来的指数因子在分子分母里
   同时出现，正好约掉。

   注意 `ApplyUpdate` 那边是**另一回事**：应用方不持有新增的 `K`，
   它的下标集合仍是 `I`，所以 `π'_I = (Γ_I^{a'_K}, Δ_I^{b'_K})`，指数**要**抬。
   论文这两处分别是对的，本实现按各自推导写（并用 `check_local_view()` 自检）。

3. **`mod` 部分相交时抬的指数**

   实现时曾把 `I ∩ K = L ∉ {K, ∅}` 这一支的抬指数写成整个 `a'_K`，
   结果把 `I` 内部那部分重复计入，算出的状态通不过自检。
   正确值是 `a'_{L̄}`（只有 `K` 落在 `I` 之外的那半个）——
   与论文的 `ShamirTrick(Γ_I, Γ_L̄, F_I, F_L̄)` 写法一致。
   这是测试自己抳出来的。

### 5. 剩余未实现的部分

#### 5.1 附录 C：三种更新的零知识论证（`PoKChange` / `PoKAdd` / `PoKDelete`）

这是**唯一一块与主流程相关、但确实没做**的东西。附录 C 给了三个关系：

| 关系 | 证明什么 |
|---|---|
| `R_PoKChange` | `mod` 后的新承诺确由旧承诺与本次改动算出，且 `Γ_I^{b_I} = A' ∧ Δ_I^{a_I} = B'` |
| `R_PoKAdd` | `A^{a'_I} = A' ∧ B^{b'_I} = B' ∧ g^{a_I·b_I} = U_I` |
| `R_PoKDelete` | 被删的 `π_I` 就是新承诺，且 `A'^{a_I} = A ∧ B'^{b_I} = B ∧ g^{a_I·b_I} = U_I` |

它们对应 §8.1 的三种更新。**本实现的 §8.1 更新走的是「发布 `Υ_∆` + 对方用 `VC.Ver'` 验」**
（与 §8.2 同一套思路），因此拿不到附录 C 额外给的那点性质：

* 三个协议都是 **AoK**，能在**不公开 `F_K` 内容**的前提下证明「这次更新是合法的」。
  而 §8.1 的 `Υ_∆` 里 `mod` / `del` 必须带上旧值 `F_K`、`add` 必须带上新值 `F'_K`。
  所以只有「更新内容本身敏感」时（比如往一份医疗记录里改一条）附录 C 才必要。
* 主流程（检索 / 聚合 / 验证 / 派生）**完全不需要**它们。

补它工作量不大：`svc/pok.py` 里已有 `PoProd*` 的全部机制，
三个协议都是它的实例（`PoKDelete` 基本就是 `PoKOpen` 换个语句），
大约 +150 行代码加一个 `tests/test_pok_appendix_c.py`。

| 附录 | 内容 | 为什么没做 |

#### 5.3 §6.1 的基础协议没有单独导出

论文 §6.1 把 `PoKRep` / `PoKE*` / `PoKE2` 当作积木介绍，
本实现把它们的逻辑**内联**进了 `svc.pok.poprodstar_prove`
（随机底数 `h` 加 `z = (h^a, h^b)` 那套 `PoKE2` 做法），
没有单独导出成同名函数。功能等价，只是没有与论文接口名一一对应。

#### 5.4 §8.3 的「分块哈希」技巧

论文 §8.3 提到先把每 `ℓ_H` 比特的块哈希成 `ℓ = 2λ` 比特，
这样「`N·ℓ_H` 比特的向量」与「`N·2λ` 比特的向量」代价几乎相同
（于是 2^20 比特级的文件也能撑）。
本项目没有实现这层包装 —— `svc` 直接用 `l = 8 × 每块字节数`。
它不影响正确性，只影响能撑多大的文件。

#### 5.5 工程性缺口（不是论文的问题）

* **并行化**：素数生成与大批量模幂仍是单线程。要用 `multiprocessing` 而非线程 ——
  CPython 的 `pow(a, b, n)` 计算期间**持有 GIL**。
* **规模**：论文的 `n = 2^20` 在 Python 里跑不动
  （按实测 27 s / 1024 块线性外推，commit 一项约 7.7 小时）。
  真要上规模，得靠 5.4 的分块哈希加原生扩展。
* **服务端无持久化**：`server/app.py` 的状态全在进程内存里，
  没有认证、没有并发保护 —— 它是演示后端，不是可部署的存储服务。

## 四、实现中发现的、值得记录的坑

1. **`shamir_trick` 的同源自检不能省**。论文 §5.2 的 `VC.Agg` 里，
   `ρ_I` 与 `σ_J` 只有在两份证据来自**同一份数据**时才同源。
   攻击场景下它们不同源，`ShamirTrick` 返回 `⊥`，
   于是**连一个可验证的假证明都拼不出来**。这不是缺陷，是自净能力；
   但实现时必须真的做这个检查，否则会返回一个错误的「合并结果」。
2. **`e_∅ = 1` 而不是 0**（空乘积）。所以 `S_∅ = g^{e_[n]} = U_n`、`Λ_∅ = C`。
   测试里一开始把 `Λ_∅` 写成 1，被自己的测试纠正了 ——
   `Λ_I = 1` 只在 `I = [n]`（全体下标）时成立。
3. **素数的互异性是硬前提**，不是「最好满足」。
   哈希版映射在位数小时必然碰撞，而碰撞导致 `ShamirTrick` **静默算错**。
   所以 `PrimeGen` 默认走双射、`PrimeGenHash` 默认开启碰撞检测、
   位长不足时抛异常。
